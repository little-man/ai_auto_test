## 1. 后端：基于 `MSException` + `IResultCode` 的异常-状态码分离机制

### 核心类型
- `io.metersphere.sdk.exception.IResultCode`（`backend/framework/sdk/.../IResultCode.java`）：定义统一的错误码接口，包含 `getCode()`、`getMessage()`、`getTranslationMessage(message)` 三个方法。其 Javadoc 明确约定了错误码命名规则：6 位数字，前三位为模块号（100 通用、101 系统设置、102 项目设置、104 接口测试、105 测试跟踪、107 测试计划、108 缺陷管理、109 工作台），后三位为具体错误；同时区分两类实现——HTTP 语义的状态码使用 `MsHttpResultCode`，业务状态码由各模块自行枚举。
- `io.metersphere.sdk.exception.MSException`（`backend/framework/sdk/.../MSException.java`）：继承 `RuntimeException`，内部持有 `IResultCode errorCode`，提供多种构造器以携带错误码、消息或原始 Throwable。
- 各业务模块按领域定义自己的 `IResultCode` 枚举：例如 `ApiResultCode`（`backend/services/api-test/.../result/ApiResultCode.java`，前缀 `104xxx`）、`MsHttpResultCode`（`backend/services/system-setting/.../handler/result/MsHttpResultCode.java`，HTTP 语义码如 `100200/100400/100401/100403/100404/100500`）。
- 插件侧有独立的 `MSPluginException`（`backend/framework/plugin/plugin-sdk/.../MSPluginException.java`）和若干业务专用 checked exception（如 `RegexpIllegalException`、`TypeNotMatchException`、`UninitializedException`、`CustomFieldValidateException`）。

### 全局异常处理器
`RestControllerExceptionHandler`（`backend/services/system-setting/.../handler/RestControllerExceptionHandler.java`）通过 `@RestControllerAdvice` 集中拦截：
- `MethodArgumentNotValidException` → 400，返回字段级校验错误 Map。
- `HttpRequestMethodNotSupportedException` → 405。
- `MSException` → 若 errorCode 是 `MsHttpResultCode`，用 `code % 1000` 作为 HTTP 状态码；否则固定 500。所有 message 经 `Translator.get` 做国际化。
- 兜底 `Exception.class` → 500，附带完整堆栈字符串。
- `EofException` → 对静态资源请求直接返回空体，其他路径走 500。
- Shiro 相关：`ShiroException` → 401，`UnauthorizedException` → 403。
- 辅助方法 `getNotFoundMessage` 通过 `ServiceUtils.getResourceName()` 动态拼接资源名到 NOT_FOUND 提示中。

### 调用方约定
业务代码抛出 `new MSException(ApiResultCode.XXX, message)`，由上述 handler 统一转为 JSON 响应；部分服务层（如 `ApiExecuteService`）会捕获 `MSException` 并检查 `e.getErrorCode()` 做分支逻辑，体现“异常承载结构化错误码”的设计。

## 2. 前端：Axios 拦截器 + `checkStatus` 统一错误展示

- `frontend/src/api/http/checkStatus.ts`：根据 HTTP 状态码分发处理。401 触发 `logout()`；403 重定向到 `NO_RESOURCE_ROUTE_NAME`；404/405/408/5xx 显示对应 i18n 文案；对 500 且 code 为 `101511`（开源版用户数超限）或 `101512`（企业版用户数超限）做特殊弹窗引导升级。
- 支持 `errorMessageMode` 两种模式：`message`（Arco Message.error）或 `modal`（Arco Modal.error）。
- 错误文案通过 `useI18n().t('api.errMsg4xx/5xx')` 取本地化文本。

## 3. 架构与约定

- **后端**：业务异常一律抛 `MSException`，携带 `IResultCode`；HTTP 语义异常使用 `MsHttpResultCode`，业务异常使用模块自管枚举。全局 `@RestControllerAdvice` 是唯一出口，禁止 Controller 自行 try/catch 后手动封装响应。
- **错误码编码**：遵循 `IResultCode` Javadoc 中的 6 位数字规则，模块号与错误号分离，便于跨模块定位。
- **国际化**：错误 message 使用 key（如 `http_result_validate`、`api_debug_exist`），由 `Translator.get` 在 handler 层解析为当前语言。
- **前端**：不直接依赖后端业务码做 UI 分支，主要依据 HTTP 状态码；仅对两个特定业务码（101511、101512）做差异化提示，其余统一走 `checkStatus`。

## 4. 约束与规则

- 业务错误码必须实现 `IResultCode`，并使用 6 位数字编码，前三位为模块号（见 `IResultCode` Javadoc 注释）。
- HTTP 语义状态码应使用 `MsHttpResultCode`，其值后三位即 HTTP 状态码（见 `MsHttpResultCode` Javadoc）。
- 控制器层统一通过 `RestControllerExceptionHandler` 处理异常，新增异常类型需在此注册 `@ExceptionHandler`。
- 前端错误展示统一走 `checkStatus`，新增 HTTP 状态码分支需在此补充映射。
- 未知异常最终由兜底 `Exception.class` 处理器返回 500 及堆栈，用于生产排查。
